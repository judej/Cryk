# Cryk development plan

**Revision 1 · November 19, 2026 · PLAN_READY**

Deliver a private web app where a user connects one Gmail account, sees what they owe and what they await in two daily briefings, opens the supporting source, and corrects an obligation. During an outage, the app shows the coverage gap and continues to surface known due work. This plan uses the [v3 design](../../docs/design/service-v3.md), [Release 1 mission](mission.md), and [pilot acceptance gates](../../docs/acceptance/README.md).

The repository has Python package boundaries and seven unassigned tickets. The first executable migration, application entry point, dependency pins, and test harness belong to P01. **The first implementation decision is approval of P01 against this revision.** Later tickets follow the existing dependency chain. The developer controls merge, live access, deployment, enrollment, and release.

## Build order and acceptance evidence

Each row starts after independent acceptance of its predecessor. Migrations travel with the behavior they protect. Tests use synthetic identities, messages, clocks, and provider responses. Use real PostgreSQL connections and runtime roles wherever the claim concerns database authority, concurrency, or rollback.

## First implementation assignment

Start with **one P01 worker** on a feature branch after approval. The proposed write scope is `pyproject.toml` and its lockfile, `src/cryk/api/`, `src/cryk/storage/`, `alembic.ini`, `migrations/`, `tests/identity/`, and the P01 ticket evidence. Keep local setup and verification commands in `tests/README.md`. The planner owns the [ticket index](README.md) and [run record](run.md). Confirm any additional shared path before editing it.

1. Create the smallest runnable FastAPI application and PostgreSQL migration. Separate the migration owner from runtime roles. Define a tenant, issuer/subject mapping, server-side session, and one tenant-owned record. Exercise fixtures using the same runtime grants as the service.
2. Wire sign-in, callback, protected read, one authenticated local change, and logout. Verify authorization code with PKCE, state, nonce, issuer and audience. Use secure HTTP-only cookies and CSRF checks. Resolve tenant scope from the verified session. Document how the identity service enforces the design's authentication requirements.
3. Follow one user through sign-in, read, change, logout, denied reuse, and fresh sign-in. Repeat with a second tenant and a record it does not own. Confirm the database denies cross-tenant reads and changes even when exercised directly under the applicable role. Check device revocation and recovery invalidate the intended sessions. Cover the distinction between session logout and mailbox-grant withdrawal in the session contract, then exercise it with a connection in P02.
4. Record exact setup, migration, API start, focused test, and OpenAPI verification commands in the ticket with their results and reviewed revision or change digest. Hand the change to an independent reviewer. Advance P02 after acceptance and integrated checks.

## Interfaces that later tickets share

| Interface or resource | Introduce it in | Extend it in dependency order |
| --- | --- | --- |
| Versioned API, tenant-scoped database access, migration chain | P01 | Add connection, coverage, action, briefing, and withdrawal contracts with their tickets. Keep link opens side-effect free. Serialize migration and contract changes. |

| PostgreSQL jobs and capacity | P03 | Claim in a short transaction, release before network calls, and commit results with follow-up work. P04 adds spending controls and P05 reserves due-work capacity. Scheduler access is limited to control fields, with provider networking and decryption excluded. |
| Content handling and operations | P02 | Establish separate credential and derived-content keys and content-free telemetry before introducing mail reads. P04 carries source restrictions into derived facts. P05 generates descriptions transiently and falls back to saved facts with checked time. Assign one writer per path. Before each later ticket starts, record its exact paths, shared fixtures, migration predecessor, and test resources. For each ticket the worker records commands, results, remaining gaps, and the change revision. The independent reviewer traces a normal entry point and its failure and recovery cases. The planner records acceptance for that revision and reruns applicable checks after integration.

## Decisions and release gates

| When | Decision owner and recommended choice | Consequence |
| --- | --- | --- |
| Before implementation | Developer approves P01 against revision 1. Start with synthetic sign-in and a local PostgreSQL instance. | The team can demonstrate the first protected user path without mailbox access or hosting spend. |
| Before environment setup or live access | Developer names the operator and privacy owner and approves deployment cost and key service. Use the design's Linux, HTTPS, private networking, TLS, Keycloak, and OpenBao Transit reference deployment unless an equivalent passes the same checks. | The operator can assign isolated service identities and arrange independently recoverable backups and a revocation ledger. |
| Before enrollment | Service owner records eligible cohort, Google account/application status, scopes, source window including Sent, inactivity policy, and paused-account expiry. Privacy owner records processor, endpoint, feature, account settings, audience, review date, and expiry. Keep unknown or expired disclosure routes closed. | Users can consent to the actual coverage and retention terms. Enrollment depends on the isolation, privacy, and recovery evidence in P07. |
| Before evaluation | Release owner adopts numeric thresholds, sample design, and rollback conditions. Start with the proposed targets of 95% of known due actions visible within ten minutes while available, reads restored within four hours, and at most 15 minutes of lost application updates. Set detection and usefulness thresholds before examining evaluation results. | Shadow results can support an explicit release decision against agreed criteria. |

## After the pilot

**Release 2** begins after detection and usefulness meet the adopted targets and the developer approves draft work. Sequence one user-requested thread and audience check, fresh-context review of the in-memory candidate, then connector draft creation with read-back and a revision fingerprint. Gate release on changed recipients and human edits invalidating review, review timeout producing no draft, and lost responses or restore never replaying an uncertain creation.

**Release 3** begins with selected-calendar consent and interval coverage. Add free/busy time offers, recheck scheduling replies, then prepare meeting briefs on the preceding working day. A missing calendar interval yields unknown availability. Gate release on coverage, revocation, and provider-specific recovery. Other integrations each need a named owner, demonstrated need, and separate approval.
